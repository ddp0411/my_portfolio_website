I had turned a 2 to 3 hour report into one button click. Then, during testing, that
button did nothing for a few client orgs.

I opened n8n expecting red, and every execution in the log was green. As far as n8n
knew, the workflow had worked. The users still had no PDF.

That was at one of my previous jobs, where I owned the analytics and automation layer
of a SaaS platform for interior design studios: 30+ dashboards in Apache Superset and
Metabase, plus the n8n automations. I made four mistakes there that never threw an
error. Here is how each one hid, and what I check now.

## 1. I trusted a green run

The report flow: a user clicks a button, a webhook fires, n8n runs that org's SQL
through the Metabase node, and APITemplate.io renders the org's branded PDF.

The bug was an ID filter plus an IF node that checked the org ID with an "is true"
condition. Most orgs passed. A few didn't, took the other branch, and that branch
ended without doing anything, which n8n counts as a success. That's the cover image
above: every node green, and no PDF at the end.

We caught it in testing within hours, before any client saw it. Now the workflow
checks the data and the response at each step, and any path that doesn't end in a
PDF raises an alert.

## 2. I let nulls disappear inside filters

The data was messy: unstructured, stored inconsistently, full of empty fields.
Cleaning it was a big part of the job, but the nulls that hurt most hid in the
dashboard filters.

Filter by a field, and every row with a null in that field drops out. No error, and
a missing row doesn't look like anything on a chart.

```sql
-- Filtering by status silently drops tasks with no status
select status, count(*)
from tasks
where status in ('Open', 'Done')
group by status;

-- Give the missing rows their own bucket
select coalesce(status, 'Missing') as status, count(*)
from tasks
group by 1;
```

The second query has no filter. The missing rows become their own bar, so nobody has
to remember they exist.

## 3. I joined my way into bigger numbers

Two dashboards disagreed on the same metric. A one-to-many join had multiplied the
rows: a project with ten tasks had its budget counted ten times.

```sql
-- Inflated: each project repeats once per task
select sum(p.budget)
from projects p
join tasks t on t.project_id = p.id;

-- The check that caught it: same number, raw table, no join
select sum(budget)
from projects;
```

If the two differ, the join is fanning out. I now run this check on every new metric
before it reaches a dashboard.

## 4. I built a chain that could trigger itself

The task automation removed the most repetitive work on the platform. Completing a
task created the next one, and completing an activity triggered the following one.

Once, a single completion triggered the chain twice. n8n showed two clean runs, and
the duplicate task sat in the project like any other.

The fix was a guard before every create: if the next task or activity already exists
for that parent, stop. With chained automations, I now assume every trigger will
arrive twice eventually.

## What I'd tell myself on day one

**Green means nothing crashed.** It doesn't mean the user got their PDF.

**Every metric needs a raw count beside it.** When they disagree, believe the raw
count.

**Make the missing visible.** A row that drops out of a filter becomes a number
someone trusts by mistake.
